Technical description (per page)

For each page below I explain the key HTML structure, JavaScript, and design decisions that support usability, consistency, and accessibility.

profile.html

Open live page · Validation evidence

The User Profile page uses semantic HTML elements such as <header>, <nav>, <main>, and <section>. Within the main content area, I divided the page into clear sections for the introduction, profile builder controls, progress display, and profile summary. This structure improves readability and makes the page easier to follow for both visual users and screen reader users.

JavaScript prompt boxes were used because the coursework specifically required prompt() instead of a normal HTML form. I organised the logic into separate functions for each step, revisiting skipped questions, updating progress, and showing the profile summary dynamically. This allowed the page to update without reloading and made it possible to reveal completed sections progressively.

In terms of presentation, I relied on the shared stylesheet for the main page layout and added only minimal page-specific styling for interactive elements such as the profile buttons, progress track, progress bar, and step summary boxes. This kept the page visually consistent with the group website while still making the profile feature clear and usable.

sitemap.html

Open live page · Validation evidence

The Sitemap page uses the standard shared page structure with a header, main content area, “Go to top” link, and shared footer. Inside the main content, the website hierarchy is presented using an inline SVG rather than a static image. This matches the coursework requirement to create a graphical sitemap using SVG.

Each page is represented by a separate SVG node made from a rounded rectangle and text label, with connector lines showing the relationship between sections of the site. I used links inside the SVG so that each node can be clicked directly. This makes the page more interactive and gives it a real navigation function rather than making it purely visual.

Styling choices focused on spacing, alignment, hover feedback, and readability at different widths. A small amount of page-specific CSS was added only for the SVG component because the shared stylesheet does not include node, line, and focus styling for a sitemap diagram. This kept the page aligned with the shared template without replacing the group design system.

content_ST4.html

Open live page · Validation evidence

My content page was built using the shared two-column content template, with a left sidebar for internal navigation and a main content area for the article sections. The page uses one main <h1> followed by multiple <h2> and <h3> headings in a clear hierarchy. Each section has a unique id so that internal anchor links can move the user directly to the correct part of the page.

My final topic was e-waste management, with a focus on what e-waste is, its global impact, how students contribute to the problem, disposal issues, practical solutions, and sustainable tech habits. I chose this structure because it allowed the page to go into depth on one subtopic rather than covering the whole SDG too broadly.

I used the shared layout and card system from the template, then added only light page-specific styling for the content images so that they fit neatly within the design. The side navigation menu, section stack, and “Go to top” link all help the page function as a structured webpage rather than a plain article.

Challenges and lessons learned

The most significant challenges were integrating my original pages into the shared template system and refining the interactive features so that they still matched the group website.

Challenge: integrating independent work into the shared template

My original versions of the User Profile, Sitemap, and Content Page were built with their own full styling. Once Student 1 shared the final templates and stylesheet, I had to restructure my work so that it used the shared header, footer, navigation, and layout classes without losing the page-specific features I had already built.

This was especially challenging for the User Profile page and Sitemap page, because both contained unique components that were not already covered by the shared stylesheet. For the profile page, this included the prompt-driven buttons, dynamic progress bar, and summary boxes. For the sitemap page, it included the SVG node and connector styling. I solved this by keeping the shared stylesheet as the main system and adding only small page-specific CSS for custom components.

I also had to refine the scope of my content page. At first it covered multiple sustainability topics, but once the group finalised who was taking which subtopic, I narrowed my content page to e-waste management. This made the page more focused, more relevant to my role, and less repetitive with other students’ pages.

From these challenges, I learned that technical work is not only about writing code but also about integration, consistency, and adapting to shared project constraints. I also improved my confidence in using semantic HTML, JavaScript for user interaction, SVG for structure diagrams, and internal linking for long-form pages.

Accessibility considerations

I considered accessibility across all of my pages by using semantic HTML, clear heading order, meaningful link text, and a consistent page structure. Each page uses one main heading followed by lower-level headings in a logical sequence, which makes the structure easier for screen readers and keyboard users to follow.

On the content page, all images include descriptive alt text that explains the purpose of the image rather than using empty or vague labels. On the sitemap page, each SVG node includes a visible text label as well as a title so that the links are easier to interpret. On the profile page, the progress area includes a progressbar role and live progress text so that dynamic updates are more accessible.

Keyboard accessibility was also supported through the shared skip link, standard focusable links, and button controls. I avoided relying only on visual cues by maintaining readable contrast, visible headings, and straightforward navigation patterns. These choices improve usability for a wider range of users and help align the site with inclusive design expectations.

Compliance with JANET regulations

JANET guidance emphasises lawful, ethical, and responsible use of web technologies in educational contexts. The compliance material provided for the coursework highlights that student web projects should keep content appropriate and educational, avoid collecting unnecessary personal data, follow copyright rules for third-party materials, and maintain accessibility standards such as WCAG 2.1 AA.

In my own pages, I followed this by keeping the content relevant to the coursework topic and suitable for an academic audience. I did not include misleading, offensive, or inappropriate material, and I did not design any page to collect personal data beyond the temporary prompt-based interactions required for the profile task. Since the profile information is not stored externally, this avoids unnecessary handling of personal data. JANET-related guidance also stresses legal and ethical accessibility responsibilities, so I incorporated semantic structure, alt text, and keyboard-friendly navigation accordingly.

External resources were also considered carefully. My content page uses externally sourced images, so these should be acknowledged properly in the references section and treated as third-party material rather than presented as my own work. The compliance guidance specifically notes the importance of following copyright law and maintaining academic integrity, so I have been careful to keep my written content original and to distinguish my own contribution from shared team work.
